2. El módulo: Gestión de cuentas

NOM-COLAB es una suite colaborativa (texto, hojas de cálculo, presentaciones y diagramas) para docentes del CECyT 11. El módulo de cuentas es la puerta de entrada: sin una sesión válida no se puede ver ningún espacio ni documento.

Crear cuenta: nombre, contraseña (con medidor de fuerza) y empresa opcional.

Iniciar sesión. El mensaje de error es genérico para no revelar qué usuarios existen.

Casos de uso del módulo

CUCasoQué hace
CU-01Crear usuarioValida nombre (3–24 caracteres) y contraseña (mín. 8), revisa que el nombre esté libre, guarda el hash y asigna el rol USUARIO.
CU-02Iniciar sesiónBusca la cuenta con su rol (JOIN), compara el hash y crea una sesión con token y fecha de expiración.
CU-03Cerrar sesiónBorra la sesión de la base de datos; el token deja de servir.
CU-04Bloquear accesoAl 6.º intento fallido bloquea la cuenta 15 minutos.
CU-05Cifrar credencialesPBKDF2-HMAC-SHA256, 120 000 iteraciones, sal aleatoria de 16 bytes por cuenta.
CU-30Administrar usuarios y rolesSolo ADMINISTRADOR: lista las cuentas, cambia el rol y desbloquea cuentas.

4. Diseño de la base de datos

Diagrama entidad-relación del módulo de cuentas en Azure SQL.

TablaPara qué sirveLlaves
rolCatálogo de roles: 1 ADMINISTRADOR, 2 USUARIO, con su descripción.PK id; nombre único
usuarioCuenta: nombre, empresa, hash y sal de la contraseña, intentos fallidos, bloqueo y rol.PK id; FK id_rol → rol.id; nombre_clave único
sesionSesiones abiertas: token aleatorio de 256 bits, inicio y expiración (72 h).PK token; FK id_usuario (borrado en cascada)
preferenciasTema, autoguardado, versiones a conservar, calidad, movimiento.PK/FK id_usuario

Cómo se “jala” el rol (consulta real del repositorio)

SELECT u.id, u.nombre, u.hash_contrasena, u.sal, u.intentos_fallidos, u.bloqueado_hasta,
       r.nombre AS rol, p.tema, p.autoguardado_min, ...
  FROM usuario u
  JOIN rol r ON r.id = u.id_rol
  LEFT JOIN preferencias p ON p.id_usuario = u.id
 WHERE u.nombre_clave = ?          -- parámetro: nunca se concatena texto del usuario

5. Seguridad por roles

AcciónVisitanteUSUARIOADMINISTRADOR
Registrarse e iniciar sesiónSíSíSí
Espacios y documentos propios o compartidosNo (401)SíSí
Ver todas las cuentasNo (401)No (403)Sí
Cambiar roles y desbloquear cuentasNo (401)No (403)Sí (no puede quitarse su propio rol)

Cómo funciona, paso a paso

  1. FiltroSesion revisa el token de cada petición a /api/** (salvo registro e inicio de sesión). Sin token o con uno vencido o inventado: 401.
  2. Con el token busca la sesión en la base y carga al usuario con su rol (el JOIN de arriba).
  3. FiltroRol protege /api/admin/**: si el rol no es ADMINISTRADOR responde 403 “Esta sección es solo para administradores”.
  4. Como el rol se relee en cada petición, un cambio de rol aplica de inmediato, sin cerrar la sesión.
  5. La interfaz no muestra “Administrar usuarios” a un USUARIO; aunque escriba la dirección a mano, el servidor la niega.
@Component
public class FiltroRol implements HandlerInterceptor {
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        Usuario u = (Usuario) req.getAttribute(FiltroSesion.ATRIBUTO);   // lo dejó FiltroSesion
        if (u == null || !u.esAdministrador())
            throw ErrorNom.prohibido("Esta sección es solo para administradores");   // → 403
        return true;
    }
}

ADMINISTRADOR: cuentas de la BD con su rol; “Hacer administrador” y “Desbloquear”.

USUARIO que escribe la dirección a mano: el servidor responde 403.

6. Otras medidas de seguridad de la base de datos y la aplicación

MedidaDetalle
ContraseñasNunca se guardan: solo el hash PBKDF2-HMAC-SHA256 (120 000 iteraciones) con sal propia de cada cuenta. Comparación en tiempo constante.
Inyección SQLTodas las consultas usan parámetros (?) con JdbcClient; el texto del usuario nunca se concatena al SQL.
Validación de datosNombre de 3–24 letras, números, punto o guion (rechaza HTML/scripts); contraseña de 8 caracteres mínimo.
Fuerza brutaBloqueo de 15 minutos al 6.º intento; el mensaje de error no revela si el usuario existe.
SesionesToken aleatorio de 256 bits, guardado en la BD, con expiración de 72 h; al cerrar sesión se borra.
Secretos fuera del códigoURL, usuario y contraseña de la BD y la cuenta de administrador inicial son App settings de Azure (variables de entorno).
Transporte cifradoLa página solo acepta HTTPS (HTTP redirige con 301) y la conexión a la BD usa encrypt=true.
Firewall de Azure SQLSolo acepta conexiones de servicios de Azure (la Web App) y de la IP del equipo de desarrollo.
Datos locales por cuentaLas copias que el navegador guarda para trabajar sin red se separan por cuenta: otra persona en el mismo equipo no las ve.

Se siguió el mismo camino de la práctica 4 (Git y Azure con la CLI az), pero ahora con un servidor Java y una base de datos. La suscripción Azure for Students del IPN solo permite ciertas regiones; se usó westus.

Al arrancar, la aplicación crea las tablas si no existen (schema-sqlserver.sql, idempotente) y la cuenta de administrador inicial desde las variables de configuración.

9. Cómo probarlo

  1. Abrir https://nomcolab-wack.azurewebsites.net unos minutos antes (el plan gratuito se duerme; la primera entrada tarda hasta un minuto y el botón dice “Conectando con la base de datos…”).
  2. Crear cuenta nueva: queda en la base con rol USUARIO. Al entrar no aparece “Administrar usuarios”; si se escribe …/#/admin, el servidor responde 403.
  3. Entrar con la cuenta de administrador (se entrega en persona; no va en este documento): en “Administrar usuarios” aparece la cuenta recién creada, leída de Azure SQL, y se le puede cambiar el rol.
